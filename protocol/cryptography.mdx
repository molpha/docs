This is the reference for Molpha's signing math: how the eligible signer set is derived, how signatures aggregate, and the exact pipeline every verifier runs. The [Solana](/verifiers/solana), [EVM](/verifiers/evm) and [Starknet](/verifiers/starknet) verifiers and the `molpha-verifier` crate all implement it identically.

## The verification pipeline

```text
selectionSeed   = keccak256(SELECTION_SEED_PREFIX ‖ sourceId ‖ u32(registryVersion) ‖ u64(timestamp / 1000))
selectionBitmap = deriveWithoutReplacement(selectionSeed, nodeCount, groupSize)
message         = keccak256(MESSAGE_PREFIX ‖ value ‖ sourceId ‖ u32(registryVersion) ‖
                            u8(signaturesRequired) ‖ u64(timestamp) ‖ signersBitmap)
X_coalition     = Σ Xᵢ   for each signer i in signersBitmap        (plain EC sum)
challenge e     = keccak256(Pₓ ‖ Pₚ ‖ message ‖ commitment) mod Q
accept iff        popcount(signersBitmap) >= signaturesRequired
              and signersBitmap ⊆ selectionBitmap
              and ethAddress(s·G − e·X_coalition) == commitment
```

| Symbol | Meaning |
| --- | --- |
| `SELECTION_SEED_PREFIX`, `MESSAGE_PREFIX` | 32-byte hashes of ASCII labels (see [Domain separators](#domain-separators)), not the labels themselves |
| `u32`, `u64` | Big-endian integers. The seed preimage is 76 bytes, the message preimage 141 bytes |
| `timestamp` | Unix milliseconds, stamped by the gateway. See [round timing](/concepts/attestations#round-timing) |
| `X_coalition` | Plain elliptic-curve sum of the public keys of every node in `signersBitmap` |
| `Pₓ`, `Pₚ` | x-coordinate (32 bytes) and y-parity (1 byte) of `X_coalition` |
| `s` | Aggregate Schnorr scalar |
| `commitment` | Ethereum-style address (low 160 bits of the hash) of the aggregate nonce point `R` |
| `G`, `Q` | secp256k1 generator and group order |

The message has no `chainId`, so one signature is valid on every chain. Payload fields and encoding are described in [Attestations](/concepts/attestations).

## Node selection

Each round, a pseudo-random subset of the registry version's nodes (the selection set) is eligible to sign. It is derived only from values in the payload and the registry snapshot, so every verifier reproduces it independently.

```text
selectionSeed = keccak256(SELECTION_SEED_PREFIX ‖ sourceId ‖ u32(registryVersion) ‖ u64(timestamp / 1000))
groupSize     = min(signaturesRequired + redundancyBuffer, nodeCount)
```

- `nodeCount` and `redundancyBuffer` are those of the payload's `registryVersion`. Changing the buffer publishes a new registry version, so selection for an existing version never changes.
- The buffer widens the eligible set so a round can reach its quorum when some selected nodes are offline.
- Selection reads only whole seconds. All rounds of one source and registry version within the same second share one selection set.
- The caller does not choose the timestamp; the gateway stamps it. See [Security model](/protocol/security-model#selection-influence) for what that does and does not protect.

### Derivation algorithm

`deriveWithoutReplacement(selectionSeed, nodeCount, groupSize)` samples without replacement:

1. PRF: `keccak256(seed ‖ SELECTION_DOMAIN ‖ counter)`. Each 256-bit digest yields eight big-endian `uint32` limbs.
2. Bias rejection: a limb is rejected when `limb ≥ floor((2³² − 1) / nodeCount) · nodeCount`. An accepted limb maps to `limb % nodeCount`, skipping positions already chosen.
3. Complement path: when `groupSize > nodeCount / 2`, the algorithm samples the `nodeCount − groupSize` excluded nodes and complements the mask.

The complement path is why `verify` cost on Starknet is not strictly linear in signer count.

### Bitmaps

| Bitmap | Meaning |
| --- | --- |
| `selectionBitmap` | Derived: the nodes eligible to sign this round |
| `signersBitmap` | In the payload and the signed message: the nodes that actually signed |

Bit `i` is the node at 0-based index `i` of the registry version. A registry holds at most 256 nodes, one 256-bit word.

## Plain-sum aggregation

Molpha aggregates Schnorr signatures over secp256k1 by plain summation, with mandatory proof of possession at registration. It is not MuSig2: there are no delinearization coefficients and no precomputed aggregate key. The verification key for a round is the sum of the actual signers' public keys, recomputed by the verifier from the registry snapshot.

The signer set cannot be forged:

- `signersBitmap` is inside the signed message, so the signature commits to exactly which keys took part.
- A valid aggregate over keys that did not all contribute would require breaking the discrete logarithm, given that every key has a proof of possession.
- Signers must fall inside the selection set, so registered nodes cannot sign rounds they were not selected for.

### Proof of possession

Plain-sum aggregation is open to rogue-key attacks unless every key is proven to belong to its registrant. Each chain checks a Schnorr proof of possession before a key enters any registry snapshot.

| Chain | Registration | Proof message |
| --- | --- | --- |
| EVM | `addNode` | `keccak256(POP_DOMAIN ‖ verifierAddress (20 bytes) ‖ compressedPubKey)` |
| Starknet | `add_node` | Same, with the verifier address as 32 bytes |
| Solana | `register_node` | `keccak256("MOLPHA_NODE_POP_V1" ‖ program_id ‖ node_id)`, where `node_id = keccak256("MOLPHA_NODE_ID_V1" ‖ owner ‖ compressedPubKey ‖ registration_salt)` |

The Solana labels are raw ASCII, not hashed. On Solana a signing key can be registered only once (`Secp256k1KeyClaim`). EVM and Starknet reject a zero signature or commitment, off-curve keys and `s >= Q`.

The proof binds one deployment, so nodes produce one proof per chain. Proof of possession is checked only at registration, never in `verify`, so attestation signatures stay chain-agnostic.

## Domain separators

| Constant | Value | Used for |
| --- | --- | --- |
| `MESSAGE_PREFIX` | `keccak256("MOLPHA_MESSAGE_V1")` | The signed message |
| `SELECTION_SEED_PREFIX` | `keccak256("MOLPHA_SELECTION_V1")` | The selection seed |
| `SELECTION_DOMAIN` | `keccak256("MOLPHA_SELECTION_DERIVE")` | PRF inside the selection derivation |
| `POP_DOMAIN` | `keccak256("MOLPHA_VERIFIER_V1")` | Proof of possession on EVM and Starknet |

The first three are identical in every implementation. Solana uses its own proof-of-possession labels, shown above. The Solana program also uses raw ASCII labels for epoch tickets (`MOLPHA_TICKET_V1`, `MOLPHA_TICKET_ID_V1`, `MOLPHA_DISPATCH_V1`); see [Epoch settlement](/protocol/solana-program#epoch-settlement).

## The off-chain round

The node network and the gateways run the signing session: nonce commitments, message transport and retries. Whatever the transport, a verifier accepts only an aggregate that:

- covers `(value, sourceId, registryVersion, signaturesRequired, timestamp, signersBitmap)` under `MOLPHA_MESSAGE_V1`;
- comes from at least `signaturesRequired` signers, all inside the selection set;
- is a plain-sum aggregate over exactly the keys in `signersBitmap`.
